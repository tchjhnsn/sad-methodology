# SAD v3.2 — Articulation Closure as a named phase + autonomous-execution composability

This amendment captures methodology evolution from the period 2026-04-24 (v3.0.0 initial public release) through 2026-05-13. Five distinct additions, surfaced through the working application of SAD v3 to a real project (Polity-app V1 build).

## Summary of what this amendment adds

1. **Phase 1B-Final · Articulation Closure** as a named phase between Phase 1B-Final Review and Phase 2 implementation. With its own skill, deliverables, and exit criteria.
2. **The Ralph Wiggum test** as the explicit quality bar for articulation closure.
3. **Functional completion conditions** — the rule that closure conditions name user behavior, not code structure.
4. **Autonomous execution as adopted, not authored.** SAD's contribution is the articulation precondition; the executor is the community Ralph loop (Anthropic `ralph-wiggum` plugin in claude-code).
5. **Bundled-commit hygiene** and the **lockfile-with-package.json** corollary — captured operational disciplines for working with AI agents.

The amendment also surfaces three pending decisions for the methodology community: the **HTML vs. Obsidian-hygiene tension**, the **brand-load-bearing assets** rule, and the **per-deliverable explicit-vs-implicit articulation** rule.

## 1. Phase 1B-Final · Articulation Closure as a named phase

**Problem this addresses:** SAD v3 treats the Phase 1B → Phase 2 boundary as a checkpoint. In practice — observed in the Polity-app V1 build — the boundary is a *phase that must be occupied* until a cross-spec gap audit returns clean. Implementation that begins on half-closed articulation produces work that gets unwound when gaps surface later.

**Addition:** a named phase between Phase 1B Final Review and Phase 2 Implementation:

> **Phase 1B-Final · Articulation Closure.** Occupied until every UI/UX/brand/business deliverable for the version is either authored or consciously deferred with a recorded rationale. Produces an exhaustive articulation closure inventory with verification rows. Exits only when every row passes.

**Companion skill:** `skills/articulation-closure/SKILL.md`. Names the workflow steps, the deliverables, the exit criteria, and the Polity-app reference implementation paths.

**When to invoke:** Phase 1B → Phase 2 boundary (mandatory), version-boundary crossings, phase regressions when an articulation gap is discovered post-Phase-2, or any time a project asks "are we ready to implement?"

## 2. The Ralph Wiggum test

**Surfaced framing.** The discipline behind articulation closure is that the articulation should be so clear you could hand it to anyone and they implement without ambiguity. Specifically: **you should be able to hand it off to Ralph Wiggum and he couldn't get confused.**

Ralph Wiggum (from *The Simpsons*) is the canonical example of a person who would be easily confused by ambiguous instructions. He follows directions literally; he can't infer what you "really meant"; he can't fill in implied context. He represents the worst-case implementer from an ambiguity-tolerance perspective.

**The test gives articulation closure a verifiable quality bar:**

> Walk every articulation deliverable. For each line item, each section, each callout: ask *"could Ralph Wiggum implement this without asking?"* If yes, the articulation is closed for that item. If no, the gap is named and closed before the loop can run autonomously.

The Ralph Wiggum framing turns out to be the exact bar for **agentic autonomous implementation.** An autonomous agent in a Ralph loop or `/goal` loop has the same constraints: it follows the articulation literally; it can't infer what you "really meant"; it makes decisions on what is explicitly stated. If Ralph Wiggum would be confused, the agent will be too.

## 3. Functional completion conditions, not structural

**Problem this addresses:** The Polity-app V1-deploy session shipped against a structural completion condition ("every route renders, tsc passes, every ✗ becomes ✓ in the inventory"). It passed mechanical verification. But the user-facing experience was hollow — the data layer was stub-only and clicking a representative 404'd. The structural bar was met; the functional bar was never specified.

**Rule:** Final completion conditions name **user behavior**, not code structure.

- ✗ Structural: "Every route has a `page.tsx`. `tsc --noEmit` exits 0."
- ✓ Functional: "A citizen types any U.S. zip code, clicks any rep card, and reaches a real article anchored in primary sources."

Structural conditions are acceptable as **intermediate gates** within a longer plan ("typecheck passes before merge"). They cannot stand alone as the *final* completion condition for a release.

**Sub-clause to the Ralph Wiggum test:** Ralph can also confuse "the route renders" with "the user can use this." If the completion condition lets that confusion through, it is structural and must be rewritten functionally.

## 4. Autonomous execution adopted from the community

**SAD v3.0 implied that the methodology would include an execution component for Phase 2.** That implication was wrong. The Phase 2 execution layer is the community's work — Anthropic's `ralph-wiggum` plugin in claude-code, the broader Ralph loop tradition (snarktank/ralph, Geoffrey Huntley's "everything is a ralph loop"), the `/goal` slash command, awesomeclaude.ai's operational walkthroughs, claudefa.st's overnight-autonomy patterns.

**SAD's contribution is the articulation precondition.** Phase 1B-Final · Articulation Closure produces the substrate that makes the community's executor produce correct output. The two compose cleanly:

> **articulation closure → completion condition (functional) → Ralph loop → ship**

Each link is separately documented. SAD's contribution is the composition, not the executor.

**Decision recorded 2026-05-13:** adopt the community's execution layer; continue authoring the articulation layer. Re-survey quarterly; the community moves.

## 5. Operational disciplines · bundled-commit hygiene + lockfile corollary

**Two operational rules learned the hard way during the Polity-app V1 deploy cycle:**

**(a) Bundled-commit hygiene.** Every file in a staged diff is surfaced before the commit message is drafted. No "git add -A" against a working tree with accumulated changes from multiple sessions; brand changes shipping inside commits titled for other work is the specific failure this prevents.

Pre-commit ritual:

```
git diff --stat HEAD
# for any unfamiliar file: git diff HEAD -- <file>
# surface each file + ask: "intended for this commit?" "brand-load-bearing? needs explicit review?"
# only then: stage + author commit message + commit
```

**(b) Lockfile-with-package.json corollary.** When a commit touches `package.json`, the commit must also touch the lockfile (`pnpm-lock.yaml` / `package-lock.json` / `yarn.lock`). CI failing on `--frozen-lockfile` is a symptom, not a separate problem; the fix is to not separate the two in the first place. Automatable via a pre-commit git hook.

Both apply whether the agent or the human is composing the commit.

## Three pending decisions surfaced but not yet resolved

These are flagged in v3.2 amendments queued but not yet committed to canonical methodology:

**(A) HTML vs. Obsidian-hygiene tension.** SAD's deliverables ship as HTML (wireframes, brand guides, articulation inventories, methodology overviews) because HTML renders as the deliverable. But Obsidian's vault hygiene workflows (Templater, Dataview, wikilink backlinks, tag aggregation, graph view) are MD-native and don't extend to HTML. Five options surfaced (companion MD files, MD-as-source-of-truth + HTML render, custom HTML-frontmatter plugin, accept the hygiene cost, per-deliverable choice). Decision: pending.

**(B) Brand-load-bearing assets must be explicitly loaded.** Fonts, color tokens, logos — any brand-load-bearing asset must be loaded explicitly, not depend on system cascade. The Polity-app font-cascade failure is the case study. Encoded as a SAD v3.2+ rule.

**(C) Per-deliverable explicit vs. implicit articulation.** Not every page or deliverable needs explicit per-deliverable authorship. If a sitemap names a page, the brand voice covers its register, content models cover its structure, and a retrospective sweep confirms the page is reachable from a higher-level deliverable — that's enough. The discipline is *no silent absence*, not *every deliverable has its own doc*. Surfaced from the Polity-app build; encoded as a SAD v3.1+ amendment.
